让策略人员自己改规则、调分数线，并且先测算、再审批、灰度上线

一页摘要

问题

策略变更靠提需求让开发改代码，排期以周计；上线前算不清影响，上线后看不到效果；没有版本和审批记录，出问题回滚慢。

产品

一个给策略人员用的决策引擎：可视化配置规则、评分卡和决策流；改动先回溯测算，再走审批，用冠军挑战者灰度上线，全程留痕、可一键回滚。

MVP

规则 / 规则集配置、决策流（线性）、回溯测算、上线审批与版本回滚、决策 API 与原因码。冠军挑战者放 V1，可视化画布与规则健康度放 V2。

衡量

北极星：策略变更从提出到全量上线的周期（目标 1–2 周 → 2 天内，示例）。护栏：上线前做过回溯的变更占比 100%、误配置导致的回滚次数、决策 API P99 时延。

1. 背景与目标

1.1 现状：策略在代码里

贷前审批的规则和分数线写死在审批系统代码里。行业里常见的情况是：

环节现在怎么做问题
改策略策略人员写需求文档 → 开发排期改代码 → 测试 → 发版一次调整以周计；市场或风险变化时反应慢
上线前测算策略人员自己取数、在本地脚本里回溯口径不统一，评审时各说各的；有的变更干脆不测
上线方式一次性全量切换回溯只能看到历史放款客户，新放进来的人表现未知，全量切换风险大
上线后月度报表才看到通过率、坏账变化问题发现晚；很难说清哪次变更带来的影响
留痕与回滚改动记录散在需求单和代码提交里审计难追溯；出问题要重新发版才能回滚
规则存量规则只加不减没人知道哪条还有用，规则互相重叠（见《信贷审批策略分析》中 R04–R07 的增量下降）

1.2 目标

  1. 策略人员自助完成规则、分数线、决策流的配置，不再依赖开发发版；
  2. 每一次变更上线前必须回溯测算，口径由平台统一；
  3. 变更走审批 + 灰度（冠军挑战者），用真实表现决定是否全量；
  4. 所有版本可追溯、可对比、可一键回滚；
  5. 线上决策稳定、可解释：每笔决策返回原因码。

1.3 不做什么

  • 不做模型训练：评分卡 / 模型由建模团队离线产出，引擎负责部署、调用和监控；
  • 不做贷中、贷后决策（额度调整、催收分案）：领域模型预留扩展，V2 之后再评估；
  • 不替代审批系统：审批系统通过 API 调用引擎拿决策结果，进件、人工审核流程不变。

2. 用户与场景

用户要做的事最在意
策略分析师（核心用户）新增 / 调整规则，改分数线，测算影响，提交上线，看上线后效果改得快、算得准、能看到效果
策略负责人审批变更，决定灰度比例和是否全量，看整体通过率与风险变更风险可控，出问题能马上回滚
风控开发 / 运维接入新变量，保证决策服务性能与稳定配置不会拖垮线上，变量取数可监控
合规 / 审计查某次策略变更的依据、审批人、上线时间；查某笔申请为什么被拒完整留痕，拒绝理由可解释
审批系统（系统用户）每笔进件调用决策 API低时延、高可用、结果幂等

用户故事（节选）

  • 作为策略分析师，我想在页面上把“60–89 天逾期 ≥ 1 次”这条规则改成“≥ 2 次”，并立刻看到通过率和坏账率会怎么变，这样我能在评审会上用数据说话。
  • 作为策略负责人，我想先让 10% 的流量走新策略，跑够一个观察期再决定是否全量，这样新策略出问题时影响面可控。
  • 作为合规，我想输入一个申请编号，看到它命中了哪些规则、分数多少、当时生效的是哪个策略版本。

3. 核心概念

从下往上逐层组装；每一层都有版本号，策略版本是上线、审批、回滚的最小单位。

变量申请信息、征信、行为数据加工出的字段，如“近 2 年 90 天以上逾期次数”。由开发接入，有口径说明、取数超时与默认值
规则变量上的条件组合，命中后给出动作（拒绝 / 转人工 / 打标签）和原因码
规则集一组规则 + 执行方式（全部执行 / 首条命中即停）
评分卡 / 模型建模团队上传的模型文件或评分卡表，引擎负责调用
决策流把规则集、评分卡、分数分层、结果节点串起来
策略版本某一时刻决策流的完整快照，上线 / 灰度 / 回滚都以它为单位

实验（冠军挑战者）：同一入口下，冠军版本接大部分流量，一个或多个挑战者版本接小部分流量，按申请编号哈希分流，保证同一客户始终落在同一组。

4. 核心流程

4.1 策略变更生命周期

1编辑草稿基于当前线上版本复制，改规则、分数线、决策流
2回溯测算用近期样本对比新旧版本：通过率、坏账率、swap set、规则命中（必做，不做不能提交）
3提交审批附测算报告和变更说明；负责人审批，可驳回
4灰度作为挑战者接 5%–20% 流量；设熔断阈值，触发自动停流
5全量 / 回滚观察期达标后全量；未达标或出问题一键回到上一版本
6监控通过率、规则命中率、分数分布、早期逾期；异常告警

状态机：草稿 → 待审批 →（驳回 → 草稿）→ 已批准 → 灰度中 →（熔断 / 回滚 → 已下线）→ 全量生效 → 已归档。任一时刻同一入口只有一个冠军版本。

4.2 一笔申请的实时决策

进件审批系统调用 API
→
取数征信、申请、行为变量；超时用默认值或转人工
→
分流按申请编号哈希，决定冠军 / 挑战者
→
硬规则集命中即拒，记原因码
→
评分卡计算分数
→
分数分层≥ cutoff 通过；灰区转人工；其余拒绝
→
返回结果决策、分数、原因码、版本号

每笔决策完整落库（输入变量快照、各节点结果、版本号），用于审计、回溯测算和监控。

5. 功能清单与优先级

排序原则：P0 = 没有它，“自助改策略”这件事就不安全或跑不通；P1 = 让变更更有把握；P2 = 规模化之后的效率与治理。

模块功能用户优先级说明
规则规则编辑器：条件构造（变量 / 运算符 / 值 / 与或），动作与原因码策略分析师P0编辑时即时显示该规则在回溯样本上的命中率与命中坏账率（见 6.2）
规则集：执行方式、规则排序、启停策略分析师P0
决策流线性决策流：规则集 → 评分卡 → 分数分层 → 结果策略分析师P0覆盖贷前审批的主流结构
可视化画布：分支、并行、子流程策略分析师P2客群分层（新客 / 老客）复杂后再做
评分卡评分卡表上传与版本管理；分数线配置建模 / 策略P0模型文件部署（PMML 等）放 P1
回溯测算新旧版本对比：通过率、坏账率、拒绝量、swap set、规则命中策略分析师P0统一样本与口径；提交审批的前置条件（见 6.3）
收益测算：可配置好客户收益 / 坏客户损失策略负责人P1与《信贷审批策略分析》中 cutoff 选择的方法一致
上线审批流、版本 diff、一键回滚策略负责人P0回滚不需要发版，秒级生效
冠军挑战者：流量比例、观察期、熔断阈值策略负责人P1MVP 期间用“小流量全量 + 快速回滚”过渡（见 6.4）
决策服务决策 API、原因码、决策日志落库审批系统 / 合规P0见附录 API 示例
单笔决策查询：命中路径回放合规 / 客服P1输入申请编号，展示当时的版本、变量值、各节点结果
监控通过率、规则命中率、分数分布 PSI，异常告警策略分析师P1规则命中率突变往往比坏账更早暴露问题
按版本的 Vintage / 早期逾期对比策略负责人P2需要贷后数据回流
治理规则健康度：长期未命中、增量命中过低的规则提示下线策略负责人P2解决“规则只加不减”

版本规划

版本范围验收
MVP规则 / 规则集、线性决策流、评分卡表与分数线、回溯测算、审批 + 版本 + 回滚、决策 API 与日志一类产品的贷前策略全部迁入引擎；与旧系统双跑一致率 100%（同输入同结果）
V1冠军挑战者、收益测算、单笔决策回放、监控告警、模型文件部署至少一次策略变更通过灰度完成全量
V2可视化画布、按版本的 Vintage、规则健康度、更多产品接入策略变更周期稳定在目标以内

MVP 的关键前提是“双跑一致”：迁移期旧系统和引擎同时计算，结果逐笔比对，一致率 100% 后才切流。迁移出错的代价远大于晚上线。

7. 非功能需求

类别要求（示例值）为什么
时延决策 API P99 < 300 ms（不含外部征信取数）审批是用户在线等待的环节
可用性≥ 99.95%；引擎不可用时审批系统转人工，不允许默认通过风控兜底原则：宁可慢，不可放
降级单个变量取数超时 → 用配置的默认值并打标；关键变量缺失 → 转人工避免一个外部数据源拖垮整条决策
一致性同一申请编号重复调用结果一致（幂等）；分流按编号哈希，不随机避免同一客户多次申请得到不同结果
可追溯每笔决策保存变量快照、节点结果、版本号，保存期限按合规要求审计、客诉、回溯测算都依赖它
权限编辑、审批、上线分离：编辑人不能审批自己的变更内控要求

质量回溯偏差灰度实际通过率 − 回溯预测通过率绝对值 < 2 pp
稳定性决策 APIP99 时延、错误率、降级次数见第 7 节
业务护栏通过率、FPD、规则命中率按策略版本拆分；任何一项异常都优先于“变更提速”不劣于变更前

“回溯偏差”专门用来检验回溯测算本身靠不靠谱：如果灰度实际值总偏离回溯值，说明样本或口径有问题，回溯报告的结论就要打折。

9. 风险与取舍

风险应对
自助配置 = 更容易配错强制回溯 + 编辑审批分离 + 灰度 + 熔断，四道关；所有改动可一键回滚
回溯有天然盲区历史数据里只有被放款的人才有表现，新放进来的人（swap-in）表现未知。所以回溯只能用来“筛掉明显不行的方案”，是否全量要看灰度
灰度太慢逾期要几个月才显现；观察期内用通过率、规则命中率、早期逾期做先行判断，同时允许负责人在充分评估后缩短观察期并留痕
规则越配越多V2 规则健康度：长期未命中、增量命中过低的规则自动提示下线
迁移风险MVP 双跑比对，一致率 100% 才切流；先迁一类产品
做成“大而全”的平台MVP 只做线性决策流，覆盖贷前审批主流结构；画布、子流程等到客群分层确实复杂后再做

10. 附录：决策 API（示例）

请求

POST /v1/decision
{
  "request_id": "AP20261102000123",
  "product": "consumer_loan",
  "applicant": {
    "age": 34,
    "monthly_income": 8500
  },
  "bureau_ref": "BR-8f2c..."   // 征信查询凭证，引擎内部取数
}

响应

{
  "request_id": "AP20261102000123",
  "decision": "REJECT",          // APPROVE / REJECT / MANUAL
  "score": 572,
  "reason_codes": ["S01"],       // S01：综合评分未达标准
  "policy_version": "V13",
  "experiment": { "group": "challenger", "traffic": 0.1 },
  "degraded_vars": [],           // 取数超时用了默认值的变量
  "latency_ms": 86
}

原因码面向两类读者：对内（策略、合规）展示命中的具体规则；对外（客户告知）只给合规审定过的通用表述。
